# TP-7 capture workflow — 06: verified transfer queue

Prerequisite: [[TP7-CAPTURE-05]]. Before every task read the execution and experience contracts in `.maestro/playbooks/2026-09-25-TP7-Capture-Workflow/TP7-CAPTURE-01.md`, the destination matrix in `docs/tp7-capture-workflow.md`, the status vocabulary in `docs/tp7-capture-ux.md`, and current native upload safeguards. Apply the 1–3 file / under-500-line limit. Test with the existing virtual MTP infrastructure only. Next: [[TP7-CAPTURE-07]].

Outcome: durable offline drafts and an explicit, target-bound send operation with truthful verification and recovery. This is not simultaneous device-to-device streaming; sources are already safe on the Mac before the user switches instruments.

## Tasks

- [ ] **06.1 — Implement the persistent queue state model.** Extend the catalog and typed client with drafts, immutable prepared-file manifests/hashes, intended device kind, explicit confirmation binding, per-file progress, and transfer history. Define queued/preparing/awaiting-device/awaiting-confirmation/writing/verifying/verified/failed/cancelled/incomplete states and allowed transitions, and record the mapping from each to one of the at-most-five user-facing statuses in `docs/tp7-capture-ux.md`; these internal names are for the state machine and must never reach the interface. Reopen interrupted jobs as requiring reconciliation, never automatically resume writes. Preserve rendered inputs so a later edit cannot silently change an already approved payload. Completion means app restart and device absence do not lose drafts or turn uncertain work into success.

- [ ] **06.2 — Implement native destination preflight.** In a focused transfer module and `src-tauri/src/main.rs`, reuse current `mtp_upload_preset`, `mtp_upload_at_path`, and restore-preview validation patterns to inspect current device/session identity, destination roots, complete inventory, free space, target compatibility, and case-aware conflicts. Re-hash prepared files and bind the resulting plan token to manifest, destination identity, and session generation. Reject stale plans, unknown/ambiguous destinations, symlink/path escapes, and unsupported firmware/profile combinations. A missing serial must produce explicit limited-identity handling, not equality between arbitrary devices. Completion means native validation fails closed even when called without the UI.

- [ ] **06.3 — Execute prepared transfers using existing verified upload paths.** Extend the native transfer executor without weakening `mtp_upload_preset`/`mtp_upload_at_path` collision, free-space, or readback checks. Revalidate the confirmed plan immediately before mutation; write dependent sample files before the OP-XY patch manifest and verify uploaded bytes/hashes before recording success. Serialize native device work and publish structured progress/results. No overwrite/delete/rename or automatic cleanup of device objects. Stop future writes on cancel or first unsafe failure, while clearly reporting any outstanding non-interruptible operation and partial paths. Completion means a changed source, swapped device, or failed readback cannot yield a verified job.

- [ ] **06.4 — Implement safe reconciliation and retry.** Extend native transfer planning and catalog history to re-scan on reconnect and classify intended destinations as verified-identical, absent, conflicting, or uncertain. Allow retry of missing files only after a new explicit preflight/confirmation; skip identical data only after verification. An existing incomplete or conflicting preset folder must remain blocked under current upload rules unless a proven additive recovery path exists; offer a newly named copy instead of implicit deletion. Completion means retries are idempotent where proven and otherwise refuse safely with exact remedial information.

- [ ] **06.5 — Integrate transfer review, progress, and history UI.** Add a focused queue view and connect it to the phase-05 preparation panel and `DeviceConnectionBar.tsx`. Show intended versus actual device, filenames/paths, conversion summaries, space/conflicts, explicit send confirmation, current file/byte progress where the transport reports it, cancel semantics, and verification status. Use only the user-facing status vocabulary from `docs/tp7-capture-ux.md`; no internal state name, MTP code, or hash appears as primary text, and each finished job carries a one-line plain summary of what was written where. Every entry links back to the source take or region and forward to the destination artifact, so a sound on the instrument can be traced to its recording. Offer retry only where phase-06.4 proves it safe, and state what the user must do when it is not. Preserve queued work across disconnect. Reuse `deviceOperation` busy presentation for device work only — reviewing history, browsing the library, and editing regions stay available while a transfer runs — and do not mistake its counter for native serialization. Completion means every physical write needs fresh user intent, there is no “sent” toast for a partial or failed batch, and a user can tell what happened without reading an error code.

- [ ] **06.6 — Route builder sends through the confirmed queue.** Update `DrumTool.tsx`, `MultisampleTool.tsx`, and the shared preparation/queue entry point so existing Send to Device actions create a prepared draft and open destination review instead of immediately calling `mtpUploadPreset`. Reuse phase-05.3 artifacts, retain ZIP export and existing builder controls, and carry capture provenance into history. The added safety must cost one review step, not a chain of dialogs: a single destination review with one confirmation, prefilled from the remembered output type and name, and no second modal for the same intent. Completion means capture-derived or ordinary builder material cannot bypass explicit target confirmation and verification history through an older button, and sending from a builder is not slower than the immediate upload it replaces by more than that one review.

- [ ] **06.7 — Add transfer safety regression tests.** Add native fake-MTP tests and focused queue/client/component tests, splitting if needed. Cover kind/serial/session swap after preflight, missing serial, source/manifest mutation, missing roots, failed/incomplete scans, low disk space, filename collisions, wrong-device bypass attempts, user cancellation, readback mismatch, mid-batch disconnect, app restart, and reconciliation of identical/missing/conflicting files. Assert legacy builder send buttons open review without uploading, unrelated content and partial device objects are never deleted, OP-XY manifest is written last, and verified history is recorded only after readback succeeds. Assert the rendered queue and history surfaces contain none of the internal state identifiers, that a completed send is reachable in one confirmation from an already prepared draft, and that library browsing is not made inert while a transfer runs.

- [ ] **06.8 — Validate the queued cross-device workflow.** Run the targeted native transfer, queue, bridge, and UI tests plus frontend build. Update `docs/tp7-capture-validation.md` with fault-injection results and known transport limitations. Demonstrate import from a simulated TP-7, source disconnect, offline editing, target selection, failed/stale preflight, fresh confirmation, and verified send to simulated OP-XY and supported OP-1 Field targets. Completion means all state transitions and no-overwrite invariants are proven in fixtures, without claiming a real USB transfer occurred.
