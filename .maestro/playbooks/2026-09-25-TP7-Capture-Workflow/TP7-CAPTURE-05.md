# TP-7 capture workflow — 05: destination preparation

Prerequisite: [[TP7-CAPTURE-04]]. Before every task read the execution and experience contracts in `.maestro/playbooks/2026-09-25-TP7-Capture-Workflow/TP7-CAPTURE-01.md`, the evidence-backed compatibility matrix in `docs/tp7-capture-workflow.md`, and the copy and defaults in `docs/tp7-capture-ux.md`. Apply the 1–3 file / under-500-line limit. This phase prepares/exports locally; no hardware writes. Next: [[TP7-CAPTURE-06]].

Outcome: target-specific output with predictable names, formats, and locations. A raw audio file, sampler patch, drum kit, and tape are different things; label and validate them accordingly.

## Tasks

- [ ] **05.1 — Implement destination profiles and pure preparation plans.** Extend existing `src/utils/teDevices.ts` capabilities and add a focused preparation module only if needed. Define versioned OP-XY raw-sample/drum/multisample and OP-1 Field sample-import profiles using phase-01 evidence, with target paths, supported formats/channels, rate/depth conversions, duration/count limits, names, estimated sizes, and a file manifest. Separate offline compatibility checks from connected-device capacity/conflict checks. Reject unsupported, oversized, empty, or ambiguous outputs; never silently truncate or apply an OP-XY format to Field. Every profile that can be prepared must also be writable to a folder the user chooses, so a rejected or unproven device route never removes the user's ability to get the files. Express each conversion as a plain statement of what will change ("44.1 kHz, 16-bit, mono") rather than internal profile identifiers. Completion means preparation is deterministic and makes every conversion visible before any write.

- [ ] **05.2 — Connect sample regions to existing OP-XY builders.** Extend `src/hooks/useFileUpload.ts`, `src/components/drum/DrumTool.tsx`, and `src/components/multisample/MultisampleTool.tsx` (or the smallest equivalent shared handoff) to load rendered region selections through the established sample pipeline. Support ordered mapping to drum pads and explicit root-note/zone setup for melodic material. Provide both a Send to Drum lab / Send to Sample lab action on a library selection and drag-and-drop of library rows onto pads, reusing the internal drag payload and drop handling already present in `src/components/drum/DrumSampleTable.tsx` and `DrumKeyboard.tsx` rather than adding a parallel mechanism; a drag must show which pad will receive the sample before release. Refuse capacity overflow, confirm replacement of occupied pads/current work in one prompt that names what will be replaced, preserve provenance, and do not alter unrelated slots. Completion means users can build from selected captures without a Finder round trip and without losing an existing session, and assigning a clip to a pad is a single gesture.

- [ ] **05.3 — Adapt existing OP-XY generation to prepared manifests.** Compose `generateDrumPatch` / `generateMultisamplePatch` in `src/utils/patchGeneration.ts` and the destination planner into reusable local artifacts for queueing, rather than copying ZIP/schema logic into a second implementation. Validate sample references, folder names, pad/zone limits, and exported metadata after rendering. Keep existing ZIP formats/export compatible; phase-06.6 will route builder send buttons through confirmation/history rather than preserve their immediate-upload behavior. Completion means a prepared kit/multisample contains every referenced audio file and can be inspected offline with the current parser.

- [ ] **05.4 — Implement the evidence-backed OP-1 Field sample-import adapter.** Inspect `op1DrumPresetParser.ts`, `aifParser.ts`, `aiffExport.ts`, and `op1Library.ts` before extending a focused Field adapter. Implement the documented minimal sample-import route for Field firmware, validating synth/drum destination semantics, duration, format, channels, and any required metadata. Do not assume generic AIFF `INST` data creates a playable TE kit. Fully mapped kit/preset encoding is enabled only with a proven format and round-trip fixtures; otherwise expose a correctly labeled supported sample import, not a fake kit. Completion requires verifiable output structure and explicit compatibility evidence. If no supported route can be established, leave this task incomplete, record the missing evidence, and halt dependent Field transfer work instead of guessing — but keep local folder export for the prepared files available and say plainly what remains unverified and how the user can place the files themselves, rather than hiding the Field target or leaving a silent dead control.

- [ ] **05.5 — Build the destination preparation UI.** Add a focused preparation panel and wire it to the capture-library selection using existing Fieldwork control styles. Let users choose instrument/output type/name, review clips/order/channels/rate/depth/duration and destination files, resolve incompatible selections, export prepared files locally, or save a transfer draft. Remember and preselect the last used output type, name pattern, and local export folder so repeat preparation needs no re-entry, and suggest an output name from the selected material instead of blocking on an empty field. Do not choose the first connected device automatically; when a remembered device kind matches what is connected it may be offered, but it must still be shown and confirmed. State conversions and limits in plain language with the count of files that will be written, and keep Export to folder available at all times, including with no device connected or a target whose device route is unproven. Show unverified firmware support honestly and preserve prepared work when hardware is absent. Completion means OP-XY and supported Field outputs have distinct previews, a second kit takes fewer decisions than the first, and preparation never itself triggers a device write.

- [ ] **05.6 — Add preparation and builder-handoff tests.** Add targeted tests in the destination-planner tests, `useFileUpload.test.ts`, and existing patch/AIFF parser tests, splitting further if needed. Cover occupied pads, maximum counts, explicit melodic root notes, invalid names, case/Unicode collisions, different originals with equal display names, references after renaming, exact limit boundaries, rejected unsupported targets, and preserved builder sessions. Also cover drag-and-drop and Send to lab handoff onto empty and occupied pads, remembered output type/name/folder defaults across reopen, a suggested name for an untitled selection, and the local folder export path remaining available when a device target is unsupported or absent. Use independent header/schema assertions in addition to encoder/parser round trips so both sides cannot share the same unnoticed error.

- [ ] **05.7 — Validate locally prepared output.** Run targeted preparation/handoff/patch/audio tests and `npm run build`; record output manifests, fixture hashes, independently checked formats, and target capability evidence in `docs/tp7-capture-validation.md`. Compare generated fixture artifacts with documented constraints; do not write them to real devices. Completion means supported profiles pass structural checks, unsupported combinations are blocked, and hardware playability is still explicitly pending rather than inferred from a parser pass.
