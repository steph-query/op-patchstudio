# TP-7 capture workflow — 07: acceptance and Mac handoff

Prerequisite: [[TP7-CAPTURE-06]]. Before every task read the execution and experience contracts in `.maestro/playbooks/2026-09-25-TP7-Capture-Workflow/TP7-CAPTURE-01.md`, `docs/tp7-capture-workflow.md`, `docs/tp7-capture-ux.md`, and `docs/tp7-capture-validation.md`. Apply the 1–3 file / under-500-line limit. Hardware checks below are deliberately not Auto Run checkboxes.

Outcome: a tested Mac hardware-test candidate whose everyday workflow has been measured against the experience contract, not a public release or a claim of validated real-device compatibility.

## Tasks

- [ ] **07.1 — Add end-to-end acceptance fixtures and tests.** Extend `src/test/e2e/device-workflows.e2e.ts` and focused capture E2E fixtures/specs using the existing Chromium/WebKit setup. Cover TP-7 inbox → import → disconnect → offline organization → multiple regions → OP-XY preparation/send, plus the supported OP-1 Field sample-import route. Include first run with no existing library reaching a usable library without a dialog, the one-action Import new path, the keyboard-only audition-mark-name loop, drag or Send to lab handoff onto a pad, a single confirmation from prepared draft to verified send, and the local folder export fallback for an unsupported or absent device target. Include relaunch persistence, interrupted import, unsupported format, occupied builder slots, stale target confirmation, transfer failure, and retry with preserved originals. All native/device operations use fixtures and all actual test file writes stay inside workspace-owned test roots. Completion means the complete workflow is exercised without direct private state manipulation that skips the behaviors under test.

- [ ] **07.2 — Add responsive and accessibility acceptance tests.** Extend the capture-library/editor/queue component tests and browser specs with keyboard-only navigation, visible focus, editable inputs that do not trigger playback or marking shortcuts, accessible selection and error announcements, and layouts at 800 and 1440 px. Assert no document-level horizontal overflow, bounded waveform/row rendering, no lost selection when returning from an editor, no inert workspace during local import or peak building, and no shortcut collision with existing builder or macOS bindings. Capture fixture screenshots under `.maestro/tp7-capture-validation/`. Use Fieldwork tokens from `src/theme/device-themes.scss`; screenshot generation is not a claim of human visual approval.

- [ ] **07.3 — Audit the shipped experience against the contract.** Apply the experience contract and `docs/tp7-capture-ux.md`. Walk the documented happy path in the running app against fixtures and record, in `docs/tp7-capture-validation.md`, the actual user-action count for each budgeted segment — connect to imported takes, take to saved named region, region to sent kit — beside its target, naming every step the implementation added and why. Sweep the rendered UI for contract violations: internal state identifiers, MTP/PTP codes, object handles, hashes, schema versions, or absolute paths presented as primary text; empty states that do not offer both import routes; controls that are disabled with no explanation; unsupported targets with no local export fallback; and any error whose text does not name a next action, checking device errors against the transfer-mode hints in `src/utils/teDevices.ts`. Capture happy-path screenshots under `.maestro/tp7-capture-validation/`. Where a step count exceeds its target or a violation is found, add a narrowly scoped repair task rather than adjusting the target, and record anything deliberately accepted with its reason. Completion means the workflow's real cost in user actions is written down and every remaining rough edge is either fixed or explicitly accepted.

- [ ] **07.4 — Assign frontend test-build metadata.** Inspect current versions and build scripts, then assign a new local test version in `package.json` and `package-lock.json` without reusing an existing packaged version. Preserve package identity and other metadata; record the chosen version in `docs/tp7-capture-validation.md` so the next task uses exactly the same value. Do not commit, publish, or build yet. Completion means frontend package and lockfile metadata agree and no existing DMG will be overwritten by this version.

- [ ] **07.5 — Align native test-build metadata.** Set `src-tauri/Cargo.toml`, its package entry in `src-tauri/Cargo.lock`, and `src-tauri/tauri.conf.json` to the exact version selected in task 07.4. Keep `com.doxy.app`, internal command/storage identifiers, binary identity, and unrelated dependency versions unchanged. Completion means native and frontend package versions agree; test/build execution belongs to the following tasks.

- [ ] **07.6 — Run complete automated regression validation.** Run `npm test`, `npm run build`, `npm run test:e2e`, `cargo test --manifest-path src-tauri/Cargo.toml --offline`, targeted ESLint for changed TS/TSX files, and `git diff --check`. Compare with phase-01 baseline; record actual counts, commands, logs, supported/unsupported formats, and failures in `docs/tp7-capture-validation.md`. Verify source hashes remain unchanged through the synthetic workflow and old preset/session/backup data still loads. Do not tick this task while a new regression remains; add narrowly scoped repair tasks, then rerun affected checks. Existing unrelated lint debt must remain explicitly distinguished from a clean changed-file check.

- [ ] **07.7 — Document the workflow and physical acceptance procedure.** Update `docs/hardware-test-guide.md`, `README.md`, and `docs/tp7-capture-workflow.md` with verified import behavior, catalog location/recovery, offline organization, region versus original semantics, output profiles, device switching, confirmation, failure/retry handling, and real limitations. Add a short user-facing quickstart — import, audition and mark, prepare, send — written as the numbered actions a musician performs, with the keyboard map from `docs/tp7-capture-ux.md`, where the library lives, and how to move it; keep it separate from the hardware-test procedure so ordinary use is not buried in QA instructions. Include a hardware result template with app build/version/hash, macOS, instrument/firmware, source and destination names, format/duration, checksum result, on-device audition result, and observations. Preserve legacy backup/identifier documentation. Completion means a user can test disposable newly named samples without risking existing content or confusing fixture success with hardware acceptance, and can learn the everyday workflow without reading the QA guide.

- [ ] **07.8 — Build and verify an unsigned Mac test artifact.** After phase-07 automated checks pass, use the existing `npm run build:mac -- --no-sign -- --offline` path when toolchain dependencies are available, keeping output inside `src-tauri/target/`. Run `hdiutil verify` on the produced DMG and the opt-in packaged native smoke from `docs/hardware-test-guide.md`, requiring `DOXY_NATIVE_SMOKE PASS`, not just the shell exit code. Do not install to Applications, sign/notarize, access hardware, or terminate a user-running app to force smoke testing. If an existing instance prevents safe testing, record the blocker rather than reporting success. Completion requires actual build/check results and the artifact path/hash in `docs/tp7-capture-validation.md`.

- [ ] **07.9 — Produce the implementation handoff.** Review the completed phase checkboxes against `docs/tp7-capture-workflow.md`, `docs/tp7-capture-ux.md`, automated evidence, and the final diff. Update `docs/tp7-capture-validation.md` with implemented scope, exact artifact link/version, known limits, unresolved issues, the task 07.3 step counts and accepted experience gaps, and a separate **Hardware validation: pending** section unless genuine user-provided results exist. Identify any disabled destination profile instead of presenting it as complete. Completion means the handoff clearly separates software-tested behavior from pending physical checks; do not claim end-to-end hardware readiness for a blocked format or failed build.

## Manual Follow-Up — not executed by Auto Run

- Make independent verified backups first. Close competing MTP apps and use a few disposable, newly named recordings/samples; do not test against the only copy of valuable work.
- On the TP-7, capture representative mono/stereo/multichannel takes, including a long recording. Import twice, confirm originals remain byte-identical and duplicate/new status is sensible, then disconnect and reopen Fieldwork to check the offline library.
- Audition marked regions against the original; check stereo orientation/channel choice, timing, fade boundaries, normalization, naming, collections, and whether the keyboard workflow feels fast. Inspect the real UI at the Mac window sizes you use.
- Connect OP-XY, review an explicitly selected destination, send a newly named sample/kit, then load and audition it on the instrument. Repeat with supported OP-1 Field output; confirm it is playable in the intended sampler, not merely present as a file.
- Check duplicate-name refusal and safe recovery using disposable content only. Do not intentionally unplug during a write to valuable data; interruption testing needs a separately approved controlled setup.
- Judge the experience, not only the correctness: did naming several regions feel fast or tedious; did you ever wait on the app when you expected to keep browsing; did any message show a state name, code, or path you could not act on; did you ever reach a control you could not use with no explanation of why; and would you choose this over exporting to Finder by hand. Note anything you had to learn twice.
- Record outcomes in the documented hardware result template. Any firmware-specific failure requires a subsequent fix/retest pass; automated checkbox completion does not substitute for these checks.

## Deferred beyond this playbook

- Direct live TP-7 audio capture/control, cue-marker interpretation, automatic onset slicing, AI/transcription, cloud/mobile sync, marketplace/community, tape assembly, and destructive device-management actions.
- Wider target-device support or unsupported audio formats require separate evidence, implementation, and hardware validation.
